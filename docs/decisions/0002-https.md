# 0002. HTTPS

## Статус

Принято и записано в `nginx/`, `docker-compose.yml` и `deploy/`.

## Решение

Свой Nginx как reverse proxy и Certbot в отдельном запуске. Проверка владения доменом — HTTP-01 через webroot: Certbot кладёт файл в каталог, Nginx отдаёт его с `http://домен/.well-known/acme-challenge/`. Сертификат лежит в volume, который видит Nginx.

Порт 443 открывает только Nginx. Приложение сертификат не читает.

## Почему этот вариант

На одном домене цепочка видна целиком:

1. Запрос приходит на Nginx.
2. Nginx либо отдаёт файл проверки, либо проксирует на FastAPI.
3. Certbot раз в срок обновляет файлы в volume.
4. Nginx читает те же файлы.

Эту цепочку можно нарисовать и пересказать. Сертификат, конфиг и прокси — три разных предмета, их имена совпадают с вопросами на собеседовании.

Второй распространённый набор — `nginx-proxy` плюс `acme-companion`. Он сам заводит виртуальные хосты и сертификаты по переменным окружения. Его берут, когда на одном сервере много сайтов и конфиг Nginx писать вручную не хотят. Для одного учебного сайта эта автоматика прячет как раз те шаги, которые нужно уметь объяснить.

## Порядок первого выпуска

Сертификата ещё нет, а Nginx на 443 без файлов не стартует. Поэтому первый запуск на VPS такой:

1. `deploy/issue-certificate.sh` поднимает стек. Скрипт входа Nginx, если в volume ещё нет файлов Let's Encrypt, создаёт временный самоподписанный сертификат. Образ `nginx:1.27-alpine` не содержит команду `openssl`: официальный Dockerfile ставит её только чтобы проверить подпись пакетов и затем удаляет. Скрипт входа ставит пакет заново через `apk`, и только в этом случае. Приватный ключ временного сертификата в git не попадает.
2. Порт 80 отдаёт каталог проверки Certbot и проксирует точный путь `/health` в приложение. Остальной HTTP уходит редиректом на HTTPS. Поэтому `curl http://127.0.0.1/health` возвращает JSON и до выпуска настоящего сертификата, и после.
3. Certbot в отдельном запуске, профиль Compose `certificates`, пишет настоящий сертификат в volume `letsencrypt`.
4. Контейнер Nginx пересоздаётся. Скрипт входа видит файлы в volume и подставляет их путь в конфиг.
5. Тот же скрипт выпуска вызывает `deploy/install-renew-cron.sh`. В crontab пользователя появляются два запуска в сутки: 03:15 и 15:15.

Продление: `deploy/renew-certificate.sh`. Тот же webroot, затем `nginx -s reload`. Повторный запуск до срока годности ничего не заказывает. Порт 80 после выпуска не закрывают: он нужен для продления, для `/health` и для редиректа на HTTPS. Сертификат Let's Encrypt живёт около 90 дней, без crontab он истечёт.

Сертификаты живут в volume, не в git.

## Как сказать

«TLS обрывается на Nginx. Приложение говорит по HTTP внутри Docker-сети. Сертификат выпускает Certbot методом HTTP-01, файлы лежат в volume. Порт 80 оставляю для проверки домена, для `/health` и для редиректа. Продление висит в crontab два раза в сутки. Автоматический комплект nginx-proxy я не взял: для одного домена важнее видеть конфиг, чем прятать его за переменными.»
